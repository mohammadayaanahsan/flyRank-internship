Applied Search Intelligence — Capstone Report

Which pages should a content team review first — and does a learned model actually beat a written rule?

Abstract. This report asks which content pages a review team should prioritize first for refresh, given limited review capacity. Using an anonymized slice of real search performance data, a transparent baseline rule was compared against three learned models (logistic regression, decision tree, random forest) under an honest, client-grouped validation split. The random forest reached a Precision@50 of 0.68 versus the baseline's 0.50 — a real but modest lift, and far smaller than the same model's inflated 0.94 under a naive, non-grouped split. The gap between those two numbers is itself the headline finding: validation design changes the story as much as the model choice does. The result is offered as decision-support for a human reviewer, not a causal claim about what fixes a page's decline.
01 — Introduction

The problem: too many pages, too little review time

This report treats a common FlyRank client scenario as its case study: a growing content portfolio with a limited review team, where pages quietly decline in visibility without anyone noticing until traffic has already dropped. A content or SEO team rarely has time to review every page in a portfolio — some pages are stale but still get real search traffic, while others have quietly started declining. The decision this work supports is simple to state and hard to do well: out of hundreds of candidate pages, which handful should a human open first?

The answer matters because the cost of getting it wrong is asymmetric. Flagging the wrong page wastes a reviewer's limited time; missing a genuinely declining page means it keeps losing visibility unnoticed. A ranked, explainable shortlist — not a black-box verdict — is the useful output here.

02 — Data

Scope, source, and what was deliberately left out

This work uses the anonymized starter dataset released for this track (content_refresh_anonymized.csv), roughly 30,000 content pages, one row per page. It is a slice of the larger FlyRank ML Internship warehouse release, which spans a 78.8-million-row daily fact table (2025-01-27 to 2026-06-30) across 70 clients — not queried directly for this report, since the chosen lane permits building on the starter slice.

What was excluded, and why: any product-decision fields (a composite health score, priority score, or action type) are not present in this data at all — and even if they were, using them as model inputs would let a model simply copy an existing rule rather than learn anything new. No raw client names, domains, URLs, or search queries appear anywhere in this report or its underlying data.

03 — Methodology

Assumptions, features, and how the split was chosen

Unit of analysis: one content page, measured over a 90-day trailing window.

Label: a page is treated as "declining" if its trend direction over the window reads down. This is a proxy — it describes the current window, not a guaranteed future outcome — and that limitation is carried through the rest of this report rather than hidden.

Features: content age, days since last update, 90-day impressions, average search position, click-through rate, and word count — all signals observable before any review decision, never a product's own output.

Baseline: a transparent weighted rule (40% visibility, 30% freshness risk, 25% position opportunity, 5% depth gap) — the kind of scoring a team might write by hand before ever touching a model.

Validation: a client-grouped holdout split. Whole clients are held out of training entirely, so the model is tested only on clients it has never seen — protecting against the model simply memorizing one client's quirks.

04 — Results

The model beats the baseline — modestly, and only once validated honestly

Precision@K asks: of the top K pages a method ranks first, how many are actually declining? On the same client-grouped test split:

Baseline rule0.450.50
Decision Tree0.600.60
Logistic Regression0.650.66
Random Forest0.600.68

The more important comparison is what happens when the split itself changes. The same Random Forest, re-run under a naive split that ignores which client each page belongs to, looks dramatically better than it actually is:

Precision@50 — Naive random split
0.940
Precision@50 — Client-grouped split (honest)
0.680
Reading this correctly: the naive split's 0.94 is not a better model — it's the same model, tested on data it partially already knew because pages from the same client leaked across train and test. The client-grouped 0.68 is the number that should be trusted.

What the model actually leans on (Random Forest feature importance): 90-day impressions (27.5%), average position (24.9%), content age (16.1%), word count (15.7%), CTR (12.1%), days since last update (3.7%).

05 — Limitations & Honest Framing

What this can claim, and what it can't

This work is observed and directional, built on a ~30,000-row anonymized slice — not a production benchmark across the full warehouse.

The label describes the current window, not a verified future outcome, so this measures agreement with present decline rather than a forecast. No claim is made about Google's ranking algorithm, and no claim is made that refreshing a page causes it to recover — that would require a controlled experiment, which this data alone cannot provide. The ranked output is decision-support for a human reviewer, not an automated trigger.

06 — Ranked Recommendations

The action playbook

Each page in the final queue is scored by combining the model's probability (70% weight) with the baseline rule (30% weight), then tagged with reason codes a reviewer can inspect directly — never a bare number with no explanation.

  1. 1
    Open pages flagged model_decline_risk first. These crossed a 0.65 model probability threshold — the strongest, most defensible signal in this report.
  2. 2
    Then review visible_model_opportunity pages. Meaningful traffic (500+ impressions) plus moderate risk (0.50+ probability) — worth a second look even if less certain.
  3. 3
    Check ctr_review_candidate pages for title/snippet issues — good position, real traffic, but under-capturing clicks.
  4. 4
    Rule out look-alikes before acting — confirm the drop isn't a sibling page absorbing traffic, a seasonal dip, or plain low-volume noise.
  5. 5
    Never automate a change from the score alone. The queue orders review priority; a person still decides what, if anything, to change.
